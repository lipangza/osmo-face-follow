# 协议说明：Osmo Mobile SE 的 BLE + DUML 控制

本文记录本项目中真正用到、并且**在自有设备上实测验证过**的通信细节，目标是让别人可以照着复现。
所有结论都来自作者对本机蓝牙通信的观察与逐条动作验证，不包含任何厂商代码或文档素材。

## 0. 证据等级

文中每个结论都标注了等级：

| 标记 | 含义 |
| --- | --- |
| **实测** | 在真机上重复验证过，字节级可复现 |
| **推断** | 由实测数据或公开协议族常识推导，未单独做对照实验 |
| **未验证** | 代码里保留了入口，但没有可靠结论，不要当成事实 |

> 设备固件、手机蓝牙栈、系统版本都可能影响结果。换设备请先按第 9 节重新标定。

## 1. 连接与 GATT

### 1.1 广播与连接

- 设备广播名形如 `OMSE-xxxxxx-x`。本项目用「名字以 `OMSE` 开头」做自动连接匹配。**实测**
- 连接后不需要配对、绑定、PIN、激活或任何鉴权握手，直接发现服务即可读写。**实测**
- 设备没有强制要求加密链路；本项目未调用 `createBond()`。**实测**

### 1.2 服务与特征（OM SE 实测表）

| 服务 | 句柄范围 | 说明 |
| --- | --- | --- |
| `0x1800` Generic Access | `0x0001–0x0009` | 设备名、外观等 |
| `0x1801` Generic Attribute | `0x000A–0x000D` | Service Changed |
| `0x180A` Device Information | `0x000E–0x0010` | 厂商名等 |
| `0x1812` HID | `0x0011–0x001F` | 机身按键 / 摇杆相关 |
| `0xFFF0` 厂商自定义 | `0x0020–0x0028` | **控制与遥测主通道** |
| `0xFF61` | `0x0029` | 无特征，未使用 |

`0xFFF0` 服务里的三个特征：

| 值句柄 | UUID | 属性 | 用途 |
| --- | --- | --- | --- |
| `0x0022` | `FFF4` | `0x10` Notify | 设备 → 手机：遥测、状态、ACK |
| `0x0025` | `FFF5` | `0x0C` Write + Write Without Response | 手机 → 设备：DUML 命令 |
| `0x0027` | `FFF3` | `0x18` Write Without Response + Notify | 另一条可写可通知通道，本项目未使用 |

UUID 均按蓝牙基础 UUID 展开：`0000fff4-0000-1000-8000-00805f9b34fb`，其余同理。**实测**

### 1.3 MTU

- 手机请求 ATT MTU 517，设备协商结果为 **247**。**实测**
- 单次写入的有效载荷按 `MTU - 3 = 244` 字节分片。本项目所有控制帧只有 21 字节左右，不会触发分片。

### 1.4 连接流程（本项目采用）

1. 扫描，按名字前缀匹配 `OMSE`。
2. `connectGatt`，`discoverServices`。
3. `requestMtu(517)`。
4. 遍历所有服务/特征，优先选 `FFF5` 作为写通道；找不到时退化为「任意可写特征」。
5. 对所有带 Notify/Indicate 属性的特征逐个串行写 CCCD 订阅（必须等上一个描述符写完再写下一个）。
6. 之后即可写命令、从 `FFF4` 收通知。

## 2. DUML 帧格式

### 2.1 字节布局

```
偏移  字段        长度   值 / 说明
0     魔数         1     0x55
1     总长度       1     整帧字节数（含头、payload、CRC）
2     版本         1     0x04
3     CRC8         1     覆盖字节 0–2
4     sender       1     0x02（手机 App）
5     receiver     1     0x04（云台）
6     seq 低字节   1     自增序号，小端
7     seq 高字节   1
8     flags        1     0x40（与官方 App 写帧一致；0x00 也能被接受）
9     cmdSet       1     命令族，云台为 0x04
10    cmdId        1     具体命令
11…   payload      N     命令参数
末2   CRC16        2     小端，覆盖字节 0 … 总长度-3
```

- `总长度 = 4 + 7 + N + 2`；本项目的转动命令 payload 为 8 字节，所以总长度是 `0x15 = 21`。
- `seq` 每帧自增，设备 ACK 会带回同一个序号。**实测**
- sender / receiver 的地址含义是**推断**：`0x02` 是手机 App、`0x04` 是云台；
  实测中发往相机模块的帧 `receiver` 会是 `0x27`，设备上报帧的 `sender` 也可能是 `0x04` 或 `0x27`。

### 2.2 CRC8（帧头）

- 多项式：`x^8 + x^5 + x^4 + 1`（标准写法 `0x31`），**反射**实现，查表用 `0x8C`。
- 初值：`0x77`，无最终异或。
- 覆盖范围：字节 0–2，即 `55 15 04`。
- 校验向量：`CRC8(55 15 04) = A9`。**实测**（真机帧头恒为 `55 15 04 A9`）

```text
crc = init
for byte in data:
    crc = table8[(byte ^ crc) & 0xFF]
```

### 2.3 CRC16（整帧）

- 多项式：CCITT `0x1021`，**反射**实现，查表用 `0x8408`。
- 初值：**`0x3692`**，无最终异或。
- 覆盖范围：**从 `0x55` 到 payload 最后一个字节**（即整帧去掉末尾 2 字节）。
- 结果按小端写入帧尾。
- **实测**：用这组参数重算真机发出的 21 字节控制帧，得到的 CRC 与抓到的字节完全一致。
  早期流传的「初值 `0xDF0C`、只算 body+payload」是错的，组出来的帧会被设备静默丢弃。

```text
crc = 0x3692
for byte in frame[0 : len-2]:
    crc = (crc >> 8) ^ table16[(byte ^ crc) & 0xFF]
```

## 3. 云台转动命令

### 3.1 payload 布局（8 字节）

| 偏移 | 类型 | 字段 |
| --- | --- | --- |
| 0–1 | int16 LE | yaw |
| 2–3 | int16 LE | roll |
| 4–5 | int16 LE | pitch |
| 6 | uint8 | mode |
| 7 | uint8 | time（秒，本项目固定 1） |

**注意顺序是 yaw / roll / pitch，roll 在中间。** 很多参考实现会写成 yaw/pitch/roll，导致俯仰无效。**实测**

`mode` 取值：

| mode | 含义 | 证据 |
| --- | --- | --- |
| `0x04` | 相对角度 | **实测**（俯仰轴用它） |
| `0x05` | 绝对角度 | **推断**（未做对照实验） |
| `0x80` | 速度模式 | **实测**（yaw 用它） |

### 3.2 yaw 速度控制

- `cmdSet = 0x04`，`cmdId = 0x0C`，`mode = 0x80`。
- 换算：**角速度(°/s) = value × 0.1**。
- 限幅：`±1200`，对应官方上限 120°/s。
- 例：`value = 300` → 30°/s；`value = 0` → 停。

**实测**：正负号对应左右转向；`value` 为 0 时云台停止。方向与手机画面 `offsetX` 同号
（人脸偏右 → 正值 → 云台右转），如果实际方向相反，把代码里的 `FOLLOW_YAW_SIGN` 取 `-1`。

### 3.3 pitch 角度控制

- `cmdSet = 0x04`，`cmdId = 0x14`，`mode = 0x04`（相对角度）。
- 换算：**角度(°) = value × 0.1**。
- 实测：`value = +300` → 云台俯仰约 30.1°。
- **俯仰轴在 `cmdId = 0x0C` 的速度帧里不生效**，必须用角度帧。**实测**
- 官方机械范围：pitch `-106.54° ~ +235.5°`。软件层应自行加限位，不要贴着机械限位跑。

### 3.4 其它轴

- roll 的控制未验证；payload 里保留字段但本项目始终填 0。
- yaw 使用 `cmdId = 0x14` 的角度模式未验证（本项目 yaw 只用速度模式）。

## 4. ACK 与遥测

- 设备对每一条合法控制帧，会在 **20–30 ms** 内通过 `FFF4` 回一条 ACK：
  **序号相同、`flags = 0x80`**。**实测**
- 收不到 ACK 通常意味着：CRC 错、长度字段错、payload 长度不对，或 receiver 写错。
- `FFF4` 同时持续推送遥测帧（数量很大）。本项目只做解析和日志，不把遥测当控制闭环输入。
- **实测观察**：直接用机身物理摇杆拨动云台时，BLE 上没有对应的控制写帧，只有遥测数值变化；
  说明物理摇杆是云台本地闭环。想抓真实控制帧，必须在 App 内用屏幕摇杆操作。

## 5. 示例帧

以下字节由本仓库的 `DumlProtocol.kt` 生成，可用于对照实现是否正确（**不是**设备回包）：

```text
# 零速度，seq=1，flags=0x40
55 15 04 A9 02 04 01 00 40 04 0C 00 00 00 00 00 00 80 01 FA 33

# yaw = +50（即 5.0°/s），seq=2，速度模式，time=2
55 15 04 A9 02 04 02 00 40 04 0C 32 00 00 00 00 00 80 02 71 E9

# pitch = +30（即 3.0°），seq=3，相对角度模式，time=1
55 15 04 A9 02 04 03 00 40 04 14 00 00 00 00 1E 00 04 01 B1 3E

# yaw = -300（即 -30.0°/s），seq=4，速度模式，time=1
55 15 04 A9 02 04 04 00 40 04 0C D4 FE 00 00 00 00 80 01 26 D2
```

解码第一条：`55` 魔数、`15` 总长 21、`04` 版本、`A9` CRC8、`02` 手机、`04` 云台、
`01 00` 序号 1、`40` flags、`04` cmdSet、`0C` 速度命令、payload 全零、`FA 33` CRC16。

真机验证方法：把某条帧发出去，若设备在 30 ms 内回同序号 ACK，且云台按预期动作，即说明实现正确。

## 6. 标定方法（换设备必做）

### 6.1 安全前提

- 云台**空载、离开桌面、手不要碰**，避免堵转。
- 一次只改一个变量，一次只动一个轴。
- 每条实验帧前后各发一帧零速度，实验结束立刻停止发送。
- 先确认能收到 ACK，再观察机械动作。

### 6.2 步骤

1. **确认链路**：连接后发一条零速度帧，确认 30 ms 内收到同序号 ACK。
2. **标定 yaw 单位**：发 `cmdId=0x0C, mode=0x80, yaw=+300, time=1`，用手机指南针或
   目测记录 1 秒内转过的角度。若约 30°，则单位是 0.1°/s；按比例修正。
3. **确认 yaw 符号**：`+300` 实际向右转，则 `FOLLOW_YAW_SIGN = +1`，否则取 `-1`。
4. **标定 pitch 单位**：发 `cmdId=0x14, mode=0x04, pitch=+300, time=1`，记录实际俯仰角，
   确认 0.1°/单位与正负方向。
5. **确认速度帧对 pitch 无效**：改用 `cmdId=0x0C, mode=0x80, pitch=+300`，若云台不动，
   说明俯仰必须走角度模式。
6. **测机械限位**：小步进（每次 5–10°）逼近上下限，记录实际极限；软件限位应留 10° 以上余量。

### 6.3 本项目提供的标定入口

`MainActivity` 支持通过 adb intent 单发一帧（避免误触）：

```bash
adb shell am start -f 0x20000000 -n com.example.facefollow/.MainActivity \
  --ei m3_yaw 300 --ei m3_pitch 0 --ei m3_time 1 --ei m3_hold 500
```

执行顺序是：零速度帧 → 300 ms → 目标帧 → 保持 `holdMs` → 零速度帧。
该入口有 1.5 秒防抖，且同一时间只允许一个实验。

## 7. 跟随参数（应用层，不是设备协议）

| 参数 | 值 | 位置 |
| --- | --- | --- |
| yaw 下发频率 | 33 Hz（30 ms） | `FOLLOW_RATE_MS` |
| 死区 | `|dx| < 0.04` | `FOLLOW_DEADZONE` |
| 软拐点 | `t^1.6 × 1050`，`t = (|dx|-0.04)/0.96` | `FOLLOW_CURVE_EXP` / `FOLLOW_MAX_OUTPUT` |
| 一阶低通 | `alpha = 1 - exp(-dt/45ms)` | `smoothingTauMs` |
| 漏检保持 | 100 ms | `FOLLOW_DECAY_START_MS` |
| 漏检衰减 | 100–300 ms 线性衰减到 0 | 同上 / `FOLLOW_LOST_STOP_MS` |
| 超时停止 | > 300 ms 发零速度，之后每秒补零 | `FOLLOW_LOST_STOP_MS` |
| pitch 步进频率 | 10 Hz | `FOLLOW_PITCH_RATE_MS` |
| pitch 增益 | 满幅偏移每 100 ms 1° | `FOLLOW_PITCH_GAIN_DEG` |
| pitch 软件包络 | ±45°（相对开启姿态） | `FOLLOW_PITCH_MAX_DEG` |

这些是**应用层控制参数**，与设备协议无关；不同手机、不同镜头视场角需要重新调。

## 8. 不要做的事

- 不要公开或再分发抓包原始文件（btsnoop / HCI 日志）。
- 不要用物理摇杆去抓控制帧——它不产生 BLE 写帧。
- 不要在云台负载不平衡或贴住机械限位时长时间发速度帧。
- 不要把 `time` 字段填得很大做「持续转动」；本项目用 33 Hz 重发最新速度帧来实现持续跟随。

---

## 9. 兼容性说明

- 本表与命令字**只保证在 Osmo Mobile SE 上实测成立**。
- 其它 Osmo Mobile 型号可能复用同一命令族，但 `cmdId`、单位、限位可能不同，必须重新标定。
- 若设备固件升级后行为变化，优先检查：帧头 CRC8、CRC16 初值、payload 顺序、`mode` 取值。
